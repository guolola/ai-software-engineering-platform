# 模型选择指南

## 适用场景

当供应商返回多个模型，而你需要为需求、UML、设计、代码、测试或文档任务选择合适模型时，使用本指南。

## 入口位置

先在账号设置的 Provider 管理中发现模型并完成连接测试，再回到项目工作台选择当前生成任务使用的模型。

## 前置条件

- Provider 已连接成功并返回当前可用模型。
- 已了解供应商的上下文限制、计费、速率限制和数据处理政策。
- 已准备一个可重复的代表性项目作为验证样例。

## 操作步骤

1. 从供应商当前返回的模型中筛选支持所需上下文长度的候选项。
2. 用小型任务验证 JSON、工具调用和流式输出兼容性。
3. 用同一份需求比较结构完整性、PlantUML 可修复性和追踪 ID 稳定性。
4. 记录成功率、耗时和供应商账单，再选择默认模型。
5. 对代码原型和长文档等不同任务分别验证，不假设一个模型适合全部阶段。

选择时优先考虑可靠的结构化输出、指令遵循和稳定性，其次再权衡速度与成本。模型名称、排名和可用区域变化较快，因此本手册不维护固定 Top10。

## 结果与产物

- 已通过当前 Provider 连通性与兼容性测试的候选模型
- 针对不同生成阶段的默认模型选择
- 可复用的质量、延迟、成功率和成本比较记录

## 映射关系

Provider 决定可发现的模型集合；项目任务记录实际使用的模型；运行历史、结构校验、渲染结果和追踪覆盖共同构成选型证据。

## 常见问题

**为什么不再提供固定模型排行榜？**

模型版本、供应商路由、价格和可用性会持续变化。用当前账号和真实工作流验证，比静态排名更可靠。

**参数量更大就一定更好吗？**

不一定。平台更依赖结构化输出、长上下文、稳定 ID 和可修复 PlantUML，实际成功率比单一规模指标更重要。

**如何控制成本？**

先用短样例筛选兼容模型，再对少量完整链路比较。供应商产生的真实费用以其账单为准。
